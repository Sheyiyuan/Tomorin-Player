# Half Beat Player 完善路线图

## 1. 文档目的

本文档用于指导 Half Beat Player 在现有代码基础上的安全加固、功能修复、架构收敛和发布流程完善。

当前项目已经具备完整的核心使用链路：

```text
Bilibili 登录/搜索/收藏夹导入
  -> 本地歌曲与歌单管理
  -> 音频地址解析
  -> 本地代理播放
  -> 缓存与下载
  -> 队列和播放状态恢复
```

因此，本轮完善不采用整项目重写，而采用以下策略：

> 先修复安全和用户可见问题，再为项目建立质量基线，最后渐进式重构前端状态层。

## 2. 当前基线

- 基线分支：`main`
- 最近稳定版本：`v1.2.0`
- 应用架构：Wails v2 + Go + React/TypeScript
- 后端持久化：GORM + SQLite
- 前端组件库：Mantine v8
- 当前自动化测试：无
- 当前主要质量检查：前端 ESLint，但未接入 CI

### 2.1 已实现的主要能力

- Bilibili 二维码登录、用户信息读取和登录状态恢复
- Bilibili 视频搜索、BV 号解析和收藏夹导入
- 多 P 视频解析和逐 P 添加
- 本地歌曲、歌单、队列和播放历史管理
- 音频代理、图片代理、本地缓存和歌曲下载
- 播放区间设置，可跳过片头片尾
- 列表循环、随机播放和单曲循环
- 全局音量补偿和单曲补偿覆盖
- 自定义主题、背景图片和窗口控件设置
- Windows、Linux 和 macOS 构建及打包脚本

### 2.2 当前主要问题

- 本地代理缺少严格的 URL 和目标地址限制
- 缓存 ID、歌曲 ID 等文件路径输入缺少统一校验
- 部分弹窗状态映射错误，导致已有功能无法打开
- 前端 Context、独立 Hook 和 `App.tsx` 本地状态并存
- 播放器、主题、弹窗和下载存在多套新旧实现
- 没有自动化测试、完整类型检查或 CI 质量门禁
- 发布脚本存在 macOS 和 Windows 产物风险
- README、版本号和实际实现存在不一致

## 3. 总体决策

### 3.1 采用渐进式完善

整体工作按以下比例和边界推进：

```text
约 45%：保留现有实现
约 30%：针对安全、功能和发布问题打补丁
约 25%：局部重写前端状态与弹窗架构
```

### 3.2 保留范围

以下部分原则上保留，只进行必要修复：

- SQLite 数据结构和现有用户数据
- Bilibili 登录、搜索、收藏夹和音频解析服务
- 多 P 视频数据结构与命名规则
- 共享 `<audio>` 播放引擎
- Wails 运行时等待和绑定机制
- 下载、缓存和主题图片存储的主体流程
- 当前 Mantine UI 视觉结构
- 已验证过的 Linux WebKit 兼容策略

### 3.3 局部重写范围

前端状态层需要渐进式收敛，最终形成以下唯一状态源：

```text
PlayerContext -> 当前歌曲、播放状态、队列、进度、音量、播放模式
DataContext   -> 歌曲、歌单、设置、歌词和数据缓存
ThemeContext  -> 当前主题、主题列表和主题应用逻辑
UIContext     -> 弹窗、搜索条件和临时 UI 状态
SQLite        -> 需要跨启动保留的数据
```

迁移过程中禁止长期双写。每迁移一个领域，应同时删除该领域已失去用途的旧状态和兼容代码。

## 4. 实施原则

1. 安全问题优先于新功能。
2. 用户可见断路优先于架构美化。
3. 在重构前建立可执行的质量基线。
4. 每个阶段必须能够独立发布和回滚。
5. 保持 SQLite 和已有文件数据兼容。
6. 不在同一个变更中混合安全修复、状态迁移和视觉重做。
7. 不为未确认需求增加抽象或兼容层。
8. 新代码只能接入一个明确的状态源。

## 5. 阶段一：安全与可靠性止血

**优先级：P0**

**目标：** 消除本地代理和文件操作中的高风险边界问题，修复后端基础资源管理。

### 5.1 代理目标限制

- [x] `/audio` 和 `/image` 只接受 `http` 或 `https` URL
- [x] 建立明确的 Bilibili/CDN 域名允许列表
- [x] 拒绝 URL 中的用户名、密码和异常端口
- [x] 拒绝 localhost、环回地址、链路本地地址和私网地址
- [x] 对 DNS 解析结果进行目标地址检查，避免域名解析到私网
- [x] 对每次重定向重新执行目标地址检查
- [x] 只允许代理需要的 HTTP 方法
- [x] 评估是否仍需 `Access-Control-Allow-Origin: *`，保留理由见 `docs/security-decisions.md`
- [x] 移除查询参数的重复 URL 解码

### 5.2 文件路径安全

- [x] 为缓存 ID 和歌曲 ID 定义统一的安全格式
- [x] 优先接受 UUID；兼容 BVID 时使用明确字符集
- [x] 拒绝路径分隔符、`.`、`..` 和空值
- [x] 所有 `Join` 后的路径必须验证仍位于目标目录内
- [x] 覆盖音频缓存、下载、封面和主题图片路径
- [x] 为路径校验增加单元测试

### 5.3 登录与凭据

- [x] 注销时通过过期 Cookie 或替换 CookieJar 正确清理内存会话
- [x] 注销后立即验证 `IsLoggedIn()` 返回 `false`
- [x] 明确凭据存储方案：如实声明当前为明文 SQLite 存储
- [x] 在确定安全方案前，先修正 README 中“加密存储”的错误描述
- [x] 限制数据库和数据目录权限，避免使用过宽的默认权限

### 5.4 网络与代理生命周期

- [x] API 请求客户端和长时间流式客户端使用不同超时策略
- [x] 流式播放和下载不能受 30 秒整请求超时限制
- [x] 为代理 `http.Server` 配置合理的头部和空闲超时
- [x] 修复旧代理 goroutine 覆盖新代理状态的竞争问题
- [x] 使用动态可用端口，或删除所有动态端口声明
- [x] 端口启动失败时阻止应用进入不可播放状态，或给出明确错误
- [x] 应用退出时优雅停止代理

### 5.5 数据库和资源管理

- [x] 应用退出时关闭 GORM 底层 SQL 连接
- [x] 修复删除歌曲后无法清理关联 `StreamSource` 的问题
- [x] 为 SQLite 配置合理的 busy timeout
- [x] 评估 WAL 和外键约束；启用外键并保留单连接非 WAL 模式
- [x] 评估 `SongRef` 唯一性和顺序约束方案，兼容性决策见 `docs/security-decisions.md`

### 5.6 阶段验收

- 代理不能访问 `127.0.0.1`、localhost 或私网目标。
- 重定向不能绕过目标地址检查。
- `../` 和路径分隔符不能创建、打开或删除目标目录外文件。
- 注销后当前进程立即退出登录状态。
- 超过 30 秒的播放或下载不会因共享客户端总超时中断。
- 代理停止后可稳定重启，不会被旧 goroutine 标记为停止。
- 后端安全边界测试全部通过。

## 6. 阶段二：修复用户可见功能

**优先级：P1**

**目标：** 让当前 UI 中已声明和已实现的主要功能真正可达、稳定且行为一致。

### 6.1 弹窗和操作入口

- [x] 接通歌单重命名弹窗，不再固定 `editFavModal: false`
- [x] 接通下载管理弹窗，删除空 `open` 操作
- [x] 统一 `downloadModal`、`downloadManagerModal` 和歌曲详情弹窗命名
- [x] 将完整的主题派生样式传给弹窗
- [x] 核对所有按钮对应的弹窗和 Handler 是否可达

### 6.2 播放行为

- [x] 创建 `GainNode` 时立即应用当前音量补偿
- [x] 统一音量变更和原生回退补偿的写入责任
- [x] 当前歌曲 URL 为空或过期时，播放按钮能够重新解析地址
- [x] 修复无效分 P 页码静默播放 P1 的行为
- [x] 明确多 P 视频播放区间是逐 P 配置
- [x] 修复多 P 下载命名、检测、打开和删除规则不一致
- [x] 修复缓存 403 回退与实际缓存命名不一致

### 6.3 登录与异步任务

- [x] 登录弹窗关闭时清理轮询 interval 和全部 timeout
- [x] 重新生成二维码前停止上一轮轮询
- [x] 弹窗重新打开时不显示过期二维码
- [x] 统一“BV 解析是否需要登录”的前端行为和提示

### 6.4 数据持久化

- [x] 删除重复的队列持久化调用
- [x] 每次队列或索引变化只执行一次 `SavePlaylist`
- [x] 避免在 `beforeunload` 中依赖异步 Wails 调用
- [x] 明确应用关闭时的设置、队列和播放历史保存时机
- [x] 修复删除当前主题后的主题回退行为

### 6.5 未完成能力处理

- [x] 暂时隐藏未完成的歌词入口
- [x] 明确不继续维护未连接的任务型下载管理器
- [x] 删除未连接的下载任务状态和弹窗
- [x] 替换添加歌曲流程中的原生 `prompt()`
- [x] 禁止手工输入未经本地代理的音频 URL

### 6.6 阶段验收

- 歌单可以从 UI 创建、复制、重命名和删除。
- 下载管理界面可以打开，并能打开或删除已下载文件。
- 首次播放即应用当前全局或单曲音量补偿。
- 登录弹窗关闭后不再发出轮询请求。
- 空 URL 或过期 URL 的歌曲可以通过播放按钮自动恢复。
- 每次队列变化最多产生一次持久化写入。
- README 中声明的主要功能都存在可操作入口。

## 7. 阶段三：建立质量基线

**优先级：P1**

**目标：** 在架构重构前建立最小但可靠的自动化验证能力。

- [x] 增加 `typecheck` 脚本：`tsc --noEmit`

- [x] 将 ESLint 的最大 warning 数降为 0
- [x] 删除活动代码中的 `as any`
- [x] 保持 `strict: true` 并让类型检查成为发布门禁
- [x] 增加 Vitest 和 React Testing Library

### 7.2 后端检查

- [x] 接入 `go test ./...`
- [x] 接入 `go vet ./...`
- [x] 为纯函数和安全边界补充测试
- [x] 评估 `govulncheck` 和静态分析工具；固定版本与告警策略确定前暂不接入

### 7.3 第一批测试范围

- [x] 代理 URL 协议、域名和目标 IP 校验
- [x] 文件名、缓存 ID 和歌曲 ID 校验
- [x] BV 号提取
- [x] 多 P 标题格式化
- [x] 无效页码处理

### 7.4 CI 最低门禁

```bash

cd frontend
pnpm install --frozen-lockfile
pnpm run typecheck
pnpm run lint
pnpm run build
```

### 7.5 阶段验收

- Pull Request 自动执行前后端检查。
- 类型错误不能进入构建产物。
- 安全边界存在自动化回归测试。
- `main` 只有通过验证后才能进入发布流程。
- 新增缺陷修复必须附带可复现测试，无法自动化时需记录手工验证步骤。

## 8. 阶段四：前端状态层渐进重构

**优先级：P2**

**目标：** 消除双重状态源和重复实现，使业务状态流可追踪、可测试。

### 8.1 第一步：统一弹窗状态

以 `UIContext` 为唯一弹窗状态源：

- [x] 定义类型安全的弹窗名称或显式状态字段
- [x] 删除 `App.tsx` 中手工名称适配和空操作
- [x] 删除未挂载的 `ModalContext`
- [x] 删除未使用的 `useModalManager`
- [x] 所有弹窗只通过 `UIContext` 打开和关闭
- [x] 只保留一个 Modal 容器
- [x] 使用 `React.lazy` 实现真正的代码分割

### 8.2 第二步：统一播放器状态

以 `PlayerContext` 为唯一播放器状态源：

- [x] 收敛 `currentSong`
- [x] 收敛 `queue` 和 `currentIndex`
- [x] 收敛 `isPlaying`、`progress` 和 `duration`
- [x] 收敛 `volume` 和静音状态
- [x] 统一播放模式枚举
- [x] 确保一个共享 audio 引擎只有一个状态控制者
- [x] 删除旧 Hook 或未采用的 V2 Hook，不保留两套公开入口

播放模式必须统一为一套词汇。可保留当前 UI 实际使用的：

```text
loop
random
single
```

如果选择新的枚举，则需要一次性迁移持久化配置和所有调用点。

### 8.3 第三步：统一数据状态

以 `DataContext` 为唯一数据状态源：

- [x] 收敛 `songs`
- [x] 收敛 `favorites`
- [x] 收敛当前选中歌单
- [x] 收敛 `setting`
- [x] 收敛 `lyric`
- [x] 收敛歌曲和图片缓存
- [x] 删除 `App.tsx` 和独立 Hook 中的重复数据状态
- [x] 明确后端数据加载、更新和失败回滚策略

### 8.4 第四步：统一主题状态

- [x] 只保留一个 `ThemeContext`
- [x] 主题选择必须统一调用 `applyTheme`
- [x] 统一主题的本地缓存和后端持久化责任
- [x] 删除重复的主题应用函数
- [x] 确保所有主题字段都参与保存和恢复
- [x] 删除当前主题时自动回退到默认主题

### 8.5 第五步：清理编排层

- [x] 将 `App.tsx` 缩减为领域 Hook、生命周期和页面组合
- [x] 将 `AppModalsOptimized` 的扁平 Props 收敛为按弹窗分组的类型对象
- [x] 让业务编排消费所属领域的类型化 Context/Hook，展示组件保留显式 Props
- [x] 删除 `AppModals.original.tsx` 等备份实现
- [x] 删除未使用的 props、派生值和兼容 façade
- [x] 删除重复下载管理器和无入口功能
- [x] 更新架构文档，确保描述与实际代码一致

### 8.6 迁移约束

- 一次只迁移一个领域。
- 迁移期间可以短期建立适配器，但必须有删除任务。
- 不允许旧状态和新状态长期双向同步。
- 不在状态迁移中同时重做 UI。
- 每次迁移后必须通过阶段三的全部检查。

### 8.7 阶段验收

- 当前歌曲、队列、歌曲库、主题和弹窗均只有一个状态源。
- 不再存在两套播放模式枚举。
- 队列、设置和主题不存在重复持久化。
- `App.tsx` 不再直接编排绝大多数业务细节。
- 不再保留被排除于 TypeScript/ESLint 之外的活动代码备份。
- 删除的旧实现不影响当前功能和已有数据。

## 12. 每个变更的完成定义

一项任务只有满足以下条件才能标记完成：

- 代码修改范围与任务直接相关，没有夹带无关重构。
- 新行为有自动化测试，或记录无法自动化的手工验证步骤。
- 前端类型检查、lint 和构建通过。
- 后端测试和 vet 通过。
- 涉及持久化时验证旧数据仍可读取。
- 涉及 Wails 服务方法时重新生成并核对前端绑定。
- 涉及跨平台行为时记录已验证平台和未验证平台。
- 用户可见行为或配置发生变化时同步更新文档。

## 13. 明确不做

当前完善周期不包含：

- 整项目重写
- 更换 Wails、React、Mantine 或 SQLite
- 无迁移方案地修改现有数据库结构
- 在安全和质量基线完成前大规模重做 UI
- 同时维护两套长期并行的播放器或状态系统
- 为假设中的未来需求增加通用插件架构
- 在没有测量结果时进行大范围性能重写

## 14. 风险与回滚策略

### 14.1 主要风险

- Bilibili API 和 CDN 域名可能变化，过严的允许列表可能阻断播放。
- 代理动态端口会影响前端缓存的旧代理 URL。
- 状态层迁移可能导致队列、当前歌曲或设置短期不同步。
- 数据库约束变更可能暴露现有脏数据。
- 发布脚本调整需要真实平台验证，不能只依赖语法检查。

### 14.2 控制措施

- 域名允许列表集中维护，并为已知 Bilibili CDN 样例建立测试。
- 前端不永久保存代理基础地址，启动后从后端获取当前地址。
- 状态迁移按领域进行，不一次切换全部状态。
- 增加约束前先扫描和修复已有数据。
- 每个里程碑保持可独立发布，避免超大合并。
- 数据迁移必须可重复执行，并在失败时保持原数据不变。
